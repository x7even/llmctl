# Qwen3.8-27B vs Qwen3.6-27B — throughput and code tests (2026-10-05)

Back-to-back benchmark of `qwen3.6-27b-code` and `qwen3.8-27b-code` on 4× Radeon AI PRO R9700, run by
`bench/run_comparison.py` through one llama-swap instance (:8081, separate from the live :8080 router).
Both models: FP8 weights, TP=4, MTP with 2 speculative tokens, 131K context, `--max-num-seqs 32`,
`docker.io/vllm/vllm-openai-rocm:v0.26.0`. The only profile differences are the model path, name and aliases.

The tables below are generated by `bench/make_comparison_report.py` from the saved result files; nothing is typed by hand.

## Summary

**Throughput: the two models are the same.** Across the 20 concurrent-bench levels (4 prompt sizes × concurrency 1/2/4/8/16,
32 requests each, `--no-thinking`) 19 are within about ±7.5% of each other, with no consistent winner. The one outlier is
`short-64` at concurrency 4 (3.8 is 14% slower, p90 latency 4.3 s against 2.3 s); the neighbouring levels are fine, so it is
probably a straggler in a single run, but it was not repeated. The wide sweep (1000-token prompt, exactly 1000 output tokens
on every request, concurrency 1–64) puts 3.8 between 0.2% and 1.7% below 3.6 at every level. That gap is too small to matter and
cannot be separated from the order effect (3.6 ran first). Both peak at about 1110–1130 tok/s aggregate once the 32-sequence
cap binds (concurrency 32 and above).

**3.8 writes longer answers on some prompts.** On `medium-256` it averaged about 199 completion tokens against about 166
(+20%), and 7 of the 20 concurrent-bench levels differ by more than 10% in mean output length (marked ⚠). tok/s is still comparable
there; latency and wall time are not (3.8's p90 latency is higher on `medium-256` for that reason, not because it decodes slower).

**MTP acceptance is the same in the two throughput phases and depends on the workload, not the model.** Concurrent bench: 66.5% (3.6)
vs 66.2% (3.8). Wide sweep: 97.5% vs 95.9%. The code-test phase differs (86.7% vs 75.0%) but there the two models are generating
different text, including long truncated reasoning, so it is not a like-for-like measure.

**Code tests: 3.8 did worse than 3.6 in these tests, on a small sample (4 per cell, 2 tasks, one run).**

| | 3.6-27B | 3.8-27B |
|---|---|---|
| `ttl_cache`, non-thinking | 4/4 full passes | 4/4 full passes |
| `expr_eval`, non-thinking | 2/4 full passes, 84.7% of tests passed | 1/4 full passes, 38.9% of tests passed |
| `ttl_cache`, thinking | 4/4 full passes (about 12k tokens each) | 1/4 full passes; 3 of 4 truncated at 24k tokens |
| `expr_eval`, thinking | all 4 truncated at 24k tokens | all 4 truncated at 24k tokens |

The thinking-mode results are mostly a token-budget effect and should not be read as a quality ranking: a truncated sample has no
code to grade, so it is reported as **truncated**, never as a failure. What is measurable is that 3.8 needs roughly twice the
reasoning tokens that 3.6 does on `ttl_cache` (3.8 mean 23.3k tokens against 3.6's 11.9k, with 3 of 4 cut off at the cap).
The non-thinking comparison is the cleaner one, and there 3.8 is worse on `expr_eval` (see the failure analysis below).

**Follow-up (3.8 only, see "Follow-up reruns" below):** 16 non-thinking `expr_eval` samples gave 5/16 full passes (64.2% of tests); with thinking at a 64k cap, 3.8 still
produced no `expr_eval` answer in 4/4 samples, and 3 of those 4 had collapsed into repetition loops. Sampling was temperature 0.6, not the 1.0 the 3.8 README recommends for thinking, so this is not a final verdict.

## Conditions and caveats

- **Order effect:** 3.6 ran first (09:20–11:23), 3.8 second (11:26–13:35). GPU temperature could differ slightly; the consistent
  ~1% gap in the wide sweep is within what that could explain.
- **Single run:** one run per model per level, no repeats. 32 requests per level, so a few stragglers can move a level by several percent.
- **Not comparable with the older baselines:** the figures in `CLAUDE.md` (for example 629 tok/s for 3.6 at conc=16) came from older vLLM and different
  conditions, which is why both models were re-run here. The 3.6 `medium-256` conc=16 figure is now 475 tok/s.
- **Isolation:** the live :8080 router stayed idle (`{"running":[]}`) in every snapshot and the only container running was the one under test.
- **Thinking switch:** `chat_template_kwargs: {enable_thinking: false}` was verified before each model's benchmark (0 reasoning characters), and
  all throughput numbers are no-thinking.
- **Code tests:** temperature 0.6, top_p 0.95, `max_tokens` 24000, 4 samples per task and mode, so each cell has only 4 data points.
  Tests are hidden and were validated against reference solutions (reference 18/18 and 22/22, empty solution 0/18 and 0/22).

## Failure analysis (non-thinking `expr_eval`, from the saved solutions)

Every sample's raw response, extracted solution and per-test results are saved under
`bench/results/comparison-20261005/codetests/<model>/<task>/<mode>-s<N>/`. For each sample below I checked that the response contained a single
fenced code block holding a full `evaluate` function, so these are the models' own bugs, not extraction problems.

| model | sample | score | what went wrong |
|---|---|---|---|
| 3.6 | s0 | 16/18 | `ValueError: Malformed number` on decimal literals such as `.5` and `2.`; this also fails the fuzz test |
| 3.6 | s1 | 9/18 | rejects valid input (`Unexpected end of expression`, `Unexpected operator '//'`, `Unexpected operator '-'`) |
| 3.6 | s2, s3 | 18/18 | none |
| 3.8 | s0 | 8/18 | `ValueError: Unexpected token: '/'` in 9 tests: ordinary `/` works (`7/2` gives 3.5) but the `//` floor-division operator is never recognised, so every expression using it is rejected |
| 3.8 | s1 | 1/18 | `TypeError: cannot unpack non-iterable int object` on essentially every input, even `1+2` (`parse_unary2()` returns a bare number where its caller unpacks a pair) |
| 3.8 | s2 | 1/18 | `UnboundLocalError: ... 'operand'` on essentially every input, even `1+2` (`_unary` returns `operand` before assigning it) |
| 3.8 | s3 | 18/18 | none |

The pattern differs between the models. 3.6's failures are edge cases (decimal literals, one sample's error handling) in programs that otherwise work.
3.8's failures are more severe: two of its four samples crash on every input (even `1+2`), a third never recognises the `//` operator, and the fourth is perfect.
That is a plausible sign of a model that writes long programs without checking its own control flow, but with 4 samples it is a hypothesis, not a finding.
`ttl_cache`, the task with a clear spec and an obvious data structure, was solved by both models in all four non-thinking samples.

## Thinking-mode runs: what they can and cannot say

- `expr_eval` + thinking: both models used all 24,000 tokens in all 4 samples and never produced an answer. These samples are **ungraded**.
- `ttl_cache` + thinking: 3.6 finished all 4 (11.5k–12.5k tokens, all passing). 3.8 finished 1 of 4 (21.4k tokens, passing) and was cut off at 24k in the other 3.
  3.8's true mean is therefore higher than the 23.3k shown, since 3 samples are lower bounds.
- Whether either model solves `expr_eval` with thinking was untested in the first run; the 3.8 follow-up below tried it at 64k tokens. 3.6 was not re-run at 64k.

## Follow-up reruns, 3.8 only (same day, same conditions)

Results are in `bench/results/comparison-20261005/codetests-nothink-n16/`, `codetests-think64k/` and `codetests-think64k-expr/`. Sampling was unchanged
(temperature 0.6, top_p 0.95, server-side top_k 20). 3.6 was **not** re-run, so sample counts are unbalanced (3.6 has the original 4 samples per cell).

**Non-thinking `expr_eval`, 16 samples (3.8):** 5/16 full passes, 64.2% of tests passed on average. Per-sample scores:
1, 2, 2, 2, 8, 8, 11, 14, 15, 16, 16, 18, 18, 18, 18, 18 (of 18). Four samples fail almost everything (at most 2/18). `ttl_cache` passed 16/16.
The first 4-sample result (38.9%) was therefore on the low side of 3.8's spread, but it still has the same shape: a bimodal outcome, either a working
parser or one that crashes on every input. For 3.6, the 4 samples we have scored 16, 9, 18, 18; that is too few to say the two models differ in spread.

**Thinking at 64k tokens (3.8, 4 samples per task):**

| task | result |
|---|---|
| `ttl_cache` | s0 22/22 (25.6k tokens), s3 22/22 (36.5k tokens), s1 0/22 (degenerate loop, empty answer), s2 not graded (cut at the 3600 s request timeout) |
| `expr_eval` | 0/4: all four hit the 64,000-token cap with no answer (`finish_reason=length`, 62–77 min each) |

Of the four `expr_eval` runs, three had degenerated by the cut-off: s0 repeated one sentence about `1.2.3` about 1,650 times, and s2 and s3 ended in endless runs of
`9` and `0` digits. s1 was still reasoning normally (no repetition) when it was cut. The `ttl_cache` s1 failure is the same kind: from 55% of its reasoning the model
wrote "Now, think about if … Good." 587 times, then stopped with an empty answer (`finish_reason=stop`, 40.7k tokens).
So **3 of 4 `expr_eval` and 1 of 3 finished-or-gradable `ttl_cache` thinking runs ended in repetition degeneration**, which is a failure mode of
the generation, not evidence that the model cannot solve the task (the other two `ttl_cache` samples passed).

**Caveats for this section:**
- The sampling used (temperature 0.6) is not the Qwen3.8 README's thinking recommendation (temperature 1.0, top_p 0.95, top_k 20, presence_penalty 0).
  Low temperature tends to make loops more likely, so these results may overstate how often 3.8 degenerates. This was not tested; a rerun at the
  recommended setting (and for 3.6 as well) is the obvious next step.
- Possible mitigations, none tried here: vendor sampling, `presence_penalty` 0–2 (README: reduces endless repetition, may cost some quality), lower `reasoning_effort`,
  and client-side repetition detection with abort-and-retry.
- MTP as a factor was not isolated.
- The first 64k run used a 3600 s per-request timeout in the runner, which cut 5 of its 8 samples; `run_codetests.py` now has `--timeout` (default 3600) and
  resolves `--out` to an absolute path (a relative path made the first grading pass score everything 0; the samples were re-graded from their saved solutions).
- The header line of `summary.md` in the 64k directories still says `max_tokens 24000`; the real cap was 64000.
- Decode speed with 8 concurrent long requests was only about 11–14 tok/s per request, so a 64k sample takes 1–1.3 hours.
